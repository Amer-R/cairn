Install Cairn

⚠️
Python version check

Cairn requires Python 3.10 or newer. If python --version shows 3.9 or lower, please upgrade at python.org before continuing.

Step 1 of 3 — Create a virtual environment (recommended)

A virtual environment keeps Cairn's files separate from the rest of your system — like a clean room just for this project. Strongly recommended but not mandatory.

Terminal 
# Create a folder for your Cairn projects
mkdir my-cairn-project
cd my-cairn-project

# Create the virtual environment
python -m venv .venv

# Activate it
source .venv/bin/activate

# You'll see (.venv) appear at the start of your prompt — that means it's active
PowerShell 
# Create a folder for your Cairn projects
mkdir my-cairn-project
cd my-cairn-project

# Create the virtual environment
python -m venv .venv

# Activate it
.venv\Scripts\activate

# You'll see (.venv) appear at the start of your prompt
Step 2 of 3 — Install Cairn
⚠️
Do NOT use pip install cairn

The name cairn on PyPI belongs to a completely different, unrelated package. Running pip install cairn will install the wrong thing. You must install directly from the local repo folder instead.

📦
Install from the local repo folder

Replace C:\path\to\cairn9 with the actual path to the cloned repo on your machine. The folder must contain the pyproject.toml file.

Terminal / PowerShell 
# Step 1 — clone the repo (if you haven't already)
git clone https://github.com/your-org/cairn.git
cd cairn

# Step 2 — install from the local folder (NOT from PyPI)
pip install .

# Or if you want to edit the source and see changes immediately:
pip install -e .    # -e = "editable" mode

You'll see pip install from the local pyproject.toml. When it finishes, Cairn and all its requirements are ready.

No AI model required to get started

Every command above works without a language model, an API key, or internet access. Cairn is a specification and validation toolkit — you bring the AI model later when you're ready to run for real.

The key file: context-spec.yaml

Everything Cairn does starts with one YAML file. Think of it as the "blueprint" for your AI workflow. It has four building blocks:

📋 Stages

  • What each AI agent does
  • The agent's mission
  • Hard rules it must follow

🚦 Gates

  • Human decision checkpoints
  • PASS / FAIL / ESCALATE outcomes
  • Named owner + checklist

🎓 SME Packs

  • Domain expert knowledge inputs
  • Named person + their role
  • Evidence citations + sign-off

🔗 Evidence Bindings

  • Every claim cites its source
  • Audit trail built into structure
  • No unattributed assertions
3

The Change Management Example

Cairn ships with a ready-made example: a production change management workflow. It's the perfect starting point because it covers every Cairn feature and is easy to understand without domain expertise.

📁
Where to find it

After installing Cairn, clone the repo to get the examples folder:
git clone https://github.com/your-org/cairn.git
Then navigate to: examples/change-management/context-spec.yaml

📖 Real-world scenario

A team wants to deploy a change to their production database. This is high-stakes: a bad change could cause an outage affecting thousands of users. Before anything happens, the change must be assessed, documented, approved by a Change Advisory Board (CAB), and reviewed after implementation. Every step needs a human sign-off. Every decision needs to be auditable six months from now.

This is exactly what the change-management example models.

🗺 Change Management workflow — how it flows
The actual file — examples/change-management/context-spec.yaml

This is the complete spec file that comes with Cairn. Read through it — every part is annotated to explain what it does.

examples/change-management/context-spec.yaml 
# The schema version — always starts with this
apiVersion: cairn/v1alpha
# A unique ID for this spec
spec_id: change-management
description: >
  Governance workflow for evaluating and approving infrastructure
  and software changes in regulated environments.

# ─── STAGES ────────────────────────────────────────────────────
# Each stage = one AI agent's job description
stages:

  - stage_id: assess_impact           # unique ID for this stage
    mission: >
      Analyze the scope, risk classification, and blast radius of
      the proposed change against the current system state.
    hard_rules:                        # rules the agent MUST follow
      - Must classify change as standard, normal, or emergency
      - Must identify all affected systems and downstream dependencies
      - Must produce a rollback plan before proceeding
    gate: impact_review              # which human gate runs after this stage

  - stage_id: document_change
    mission: >
      Produce a change record with full traceability to the triggering
      requirement, risk assessment, and rollback procedure.
    hard_rules:
      - Change record must reference the upstream ticket or requirement
      - Rollback procedure must be step-by-step and owner-assigned
      - Emergency changes must include a post-implementation review date
    gate: cab_approval

  - stage_id: execute_change
    mission: >
      Carry out the approved change within the maintenance window,
      following the documented procedure exactly.
    hard_rules:
      - No deviation from the approved procedure without escalation
      - Execution must be recorded with timestamps and executor identity
    gate: post_implementation_review

# ─── GATES ─────────────────────────────────────────────────────
# Each gate = a human decision point with an explicit checklist
gates:

  impact_review:
    gate_id: impact_review
    owner:   change_manager         # named role who makes the decision
    outcomes:
      - PASS
      - FAIL
      - ESCALATE
    checklist:                       # what they must verify before deciding
      - Impact classification assigned (standard/normal/emergency)
      - All affected systems identified
      - Rollback plan documented

  cab_approval:
    gate_id: cab_approval
    owner:   change_advisory_board
    outcomes: [PASS, FAIL, ESCALATE]
    checklist:
      - Change record complete and traceable
      - Risk mitigation steps documented
      - Maintenance window confirmed with stakeholders
      - Rollback procedure reviewed

  post_implementation_review:
    gate_id: post_implementation_review
    owner:   change_manager
    outcomes: [PASS, FAIL, ESCALATE]
    checklist:
      - Change executed as documented
      - No unexpected side effects observed
      - Change record closed with outcome
4

Run: cairn validate

What it does: Checks your spec file for errors in two passes. Pass 1 checks the YAML structure. Pass 2 checks that all internal references (stage → gate links, etc.) are consistent. A clean result means "zero errors guaranteed" — Cairn will never silently accept a broken spec.

1

Navigate to the repo root

Make sure you're in the same folder as the examples/ directory.

Terminal
ls examples/change-management/
# You should see: context-spec.yaml   README.md   scenarios.md   templates/
2

Run the validator

Terminal
cairn validate examples/change-management/context-spec.yaml
3

Read the result

✅ If it passes

Nothing is printed. Command exits silently. This means: zero errors, zero warnings. The spec is valid. You're ready to dry-run it.

❌ If errors are found

You'll see lines starting with Error [Schema]: or Error [Graph]: with the exact location of the problem.

Understanding error messages
Schema Error (Phase 1)
Graph Error (Phase 2)
Wrong apiVersion
Output
Error [Schema]: 'stage_id' is a required property at stages[0]
# Meaning: the first stage in your spec is missing the stage_id field
# Fix: add   stage_id: my-stage-name   to that stage
Output
Error [Graph]: Stage 'assess_impact' references gate 'impact_revew'
               which does not exist at stages[0].gate
# Meaning: you have a typo — 'impact_revew' should be 'impact_review'
# Phase 2 only runs if Phase 1 found zero errors
Output
Error [Schema]: Unknown apiVersion 'cairn/v2'. Supported: cairn/v1alpha
# This runs BEFORE any other check — always.
# Fix: change apiVersion to 'cairn/v1alpha' in your spec file
5

Run: cairn dry-run

What it does: Simulates your entire workflow from beginning to end using a "mock adapter" — a pretend AI that stands in for your real model. Every stage runs, every gate evaluates, and audit records are saved to disk. No internet. No API key. No cost.

Terminal 
cairn dry-run examples/change-management/context-spec.yaml

You'll see this output — one line per stage and gate:

Output (annotated) 
[STAGE] assess_impact      → running   ← Stage 1 starts
[STAGE] assess_impact      → done      ← Stage 1 finishes
[GATE]  impact_review      → PASS (owner: change_manager)   ← Gate 1: human decision
[STAGE] document_change    → running   ← Stage 2 starts
[STAGE] document_change    → done
[GATE]  cab_approval       → PASS (owner: change_advisory_board)   ← CAB approves
[STAGE] execute_change     → running   ← Stage 3: the change is executed
[STAGE] execute_change     → done
[GATE]  post_implementation_review → PASS (owner: change_manager)
Run complete. Gate records written to ./cairn-run-a3f7c291-8d2e-4f1a-b3c6.../
📁
A new folder appears in your directory

After running, Cairn creates a folder called cairn-run-<unique-id>/ in your current directory. This contains one JSON audit record per gate. Don't delete it — that's your audit trail.

6

Understanding the output

The gate record files

Each gate in your spec creates one JSON file in the cairn-run-<id>/ folder. This is the audit artifact. An auditor or compliance officer can read this file — alone, without talking to any developer — and reconstruct exactly what happened and who approved it.

📋 cairn-run-a3f7c291.../gate_impact_review.json PASS 
{
  "spec_id":         "change-management",
  "run_id":          "a3f7c291-8d2e-4f1a-b3c6-9e7d0f2a4b85",
  "gate_id":         "impact_review",
  "decision":        "PASS",
  "gate_owner":     "change_manager",
  "checklist_items": [
    { "item": "Impact classification assigned", "checked": true },
    { "item": "All affected systems identified", "checked": true },
    { "item": "Rollback plan documented", "checked": true }
  ],
  "timestamp":      "2026-05-20T14:23:07Z",
  "spec_version":   "cairn/v1alpha"
}
FieldWhat it tells you
spec_idWhich workflow spec this came from (change-management)
run_idUnique ID for this specific execution — links all gate records from one run together
gate_idWhich gate this record covers (impact_review)
decisionThe human decision: PASS, FAIL, or ESCALATE
gate_ownerThe named human role who made this decision
checklist_itemsEvery criterion that was evaluated — and whether it was checked
timestampExactly when the decision was recorded (ISO 8601)
spec_versionWhich schema version governed this run

Next steps

You've installed Cairn and run your first workflow. Here's where to go next, in order from beginner to advanced.

A

Start your own spec from the starter template

Copy the blank template and fill in your own workflow. It has every required field with placeholder values and comments explaining what each one needs.

Terminal
# Copy the blank starter template to your project
cp templates/starter/context-spec.yaml my-workflow.yaml

# Edit it, then validate
cairn validate my-workflow.yaml
B

Use the Cairn Consultant to design your workflow

If you're not sure how to structure your workflow, skip the YAML entirely. The Cairn Consultant (a Claude Code skill) asks you three questions and produces the spec for you.

💬
In Claude Code, type:

/cairn-consultant — then just answer the questions. No YAML knowledge needed.

C

Export agent files and connect to a real runtime

Once your spec validates, generate the agent files and connect them to a real AI runtime like LangGraph, CrewAI, or the Claude Agent SDK.

Terminal
# Generate self-contained agent files from your spec
cairn export-agents examples/change-management/context-spec.yaml

# Opens the SME knowledge capture tool in your browser
cairn sme-walkthrough
