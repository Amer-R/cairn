Cairn — Context Stack Methodology

Design governance before you choose a runtime

Cairn is a design-time framework for multi-agent systems. You define what the workflow produces, where humans decide, and what domain knowledge can't be automated — before picking a model or orchestrator. This guide walks you through Epics 1–6 with real examples, CLI commands, and interactive scenarios.

The Three-Question Adoption Path

Every Cairn adoption starts with three questions. You never hand-write YAML. The Consultant leads the conversation; cairn-compile produces the spec.

1
What decision does the workflow produce?
Not "what does the AI do" — what is the output the whole workflow is accountable for? A loan decision. A clinical note. An incident resolution. Name it precisely.
2
Where must a human decide with actual judgment?
These become gates — typed contracts with PASS/FAIL/ESCALATE outcomes, a named human owner, and an explicit checklist. Not a checkbox. A contract.
3
What knowledge lives only in domain experts?
These become SME Input Packs — a typed schema object capturing named answerer, role, evidence citations, confidence rating, and sign-off. First-class auditable artifacts.

Story 1.2 — YAML Safety Lint (CI enforced)
The CI pipeline blocks any yaml.load() call without SafeLoader — preventing arbitrary code execution from spec files. This runs on every push via lint.yml.
yaml — .github/workflows/lint.yml
name: lint
on: [push, pull_request]
jobs:
  yaml-safety:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Check yaml.safe_load usage
        run: |
          # Fail if yaml.load() is called without SafeLoader
          grep -rn "yaml\.load(" cairn/ \
            | grep -v "SafeLoader" \
            | grep -v ".pyc" \
            && echo "ERROR: unsafe yaml.load() found" && exit 1 \
            || echo "OK: all YAML loading uses safe_load"
Why this matters

A spec file containing !!python/object/apply:os.system ['rm -rf /'] can execute arbitrary code via yaml.load(). The lint gate makes this structurally impossible — not just a code-review convention.

Story 1.4 — Graph/Wiring Validation (Phase 2)

Zero false passes guarantee

A spec that exits 0 from cairn validate is guaranteed to be both structurally valid (Phase 1) AND graph-correct (Phase 2). False confidence is harder to recover from than a false negative.

1
Story 2.1 — Run a dry-run
The mock adapter executes every stage and gate in the spec deterministically — no model, no runtime. The stdout format is fixed and machine-parseable.
bash

[STAGE] intake-assessment → done

Determinism guarantee

Run the same spec twice — you get the same stage sequence and gate outcomes. The run_id changes (uuid4), but the logic is identical. This is a hard requirement, not a default behavior.

Story 2.4 — CI Validation & Dry-Run Matrix
Every spec in examples/ and domains/ is validated and dry-run on every push. New specs are auto-discovered — no workflow change needed.
yaml — .github/workflows/ci.yml
name: ci
on: [push, pull_request]
jobs:
  validate-matrix:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Install cairn
        run: pip install cairn
      - name: Validate and dry-run all specs
        run: |

            cairn validate "$spec" || exit 1

          done

Runtime Adapter Interface & Portability

An adapter engineer implements the six-function glue interface to run Cairn specs on any runtime, and verifies against the published conformance checklist. Portability becomes mechanically verifiable.

🔌

Chen — Developer Advocate, LangGraph consultancy

Chen reads spec/glue-interface.md. Six functions. Clear contracts. No ambiguity. He implements all six against LangGraph's state machine API. Runs the change-management example end-to-end. 1
Story 6.1 — The Glue Interface Specification
Six functions. One result shape. No runtime-specific references. Stable from v1alpha to v1.
load_spec(path)
Load and pre-validate a context-spec.yaml file. Calls spec_loader.py for apiVersion check before any execution.
→ {success, error, data: spec}
run_stage(spec, stage_id)
Execute a single stage in the spec. The adapter invokes the agent for that stage_id with its mission and hard rules.
→ {success, error, data: output}
evaluate_gate(spec, gate_id)
Evaluate a gate and return a decision (PASS/FAIL/ESCALATE). Must produce a gate record with all 8 required fields.
→ {success, error, data: gate_record}
collect_sme_input(spec, pack_id)
Collect SME pack answers for the named pack. May prompt a human or load from the local SME tool export.
→ {success, error, data: sme_pack}
log_artifact(spec, artifact)
Log a workflow artifact with its evidence binding. Every artifact claim must cite a traceable upstream source.
→ {success, error, data: log_entry}
handle_escalation(spec, gate_id)
Handle an ESCALATE outcome from a gate. The spec defines escalation targets — the adapter routes accordingly.
→ {success, error, data: escalation_record}
One result shape for all six functions

Every function returns {"success": bool, "error": str|None, "data": <typed>|None}. No other shapes. No exceptions propagated to adapters. This makes adapter implementations predictable and the conformance checklist mechanical.

2
Story 6.2 — Mock Adapter as Reference Implementation
The mock adapter ships with Cairn and is the reference conformant implementation. Every adapter engineer starts here — read the mock, understand the contracts, implement for their runtime.
python — adapters/mock/adapter.py (structure)
from cairn.spec_loader import load_spec_safe

def load_spec(path: str) -> dict:
    spec = load_spec_safe(path)  # handles apiVersion check
    return {"success": True, "error": None, "data": spec}

def run_stage(spec: dict, stage_id: str) -> dict:
    stage = _find_stage(spec, stage_id)
    # Mock: print progress, return success — no real model call
    print(f"[STAGE] {stage_id:<16} → running")
    print(f"[STAGE] {stage_id:<16} → done")
    return {"success": True, "error": None, "data": {"stage_id": stage_id}}

def evaluate_gate(spec: dict, gate_id: str) -> dict:
    gate = _find_gate(spec, gate_id)
    record = _build_gate_record(spec, gate, decision="PASS")
    _persist_gate_record(record)
    print(f"[GATE]  {gate_id:<16} → PASS (owner: {gate['owner']})")
    return {"success": True, "error": None, "data": record}

# ... collect_sme_input, log_artifact, handle_escalation follow same pattern

Story 6.4 — Runtime-Agnostic Portability Verification
The same context-spec.yaml runs unmodified on the mock adapter and any conformant adapter. Portability is a correctness property — not a compatibility promise.
The portability claim

A spec that passes cairn validate and runs on the mock adapter must run unmodified on any conformant adapter. The stage sequence and gate evaluation outcomes must be identical. This is verified, not assumed — and the conformance checklist is the mechanical proof.

bash — portability verification
# Step 1: validate the spec
cairn validate my-workflow.yaml

# Step 2: dry-run with mock adapter
cairn dry-run my-workflow.yaml

# Step 3: run with a real conformant adapter (e.g., LangGraph)
# Same spec — no modifications required
python -m adapters.langgraph.runner my-workflow.yaml

# Both runs should produce identical stage sequences and gate outcomes
# Only run_id will differ between the two runs
